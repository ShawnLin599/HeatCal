# 热量咔作品集案例

- 项目名称：热量咔
- 项目类型：AI 饮食记录 iPhone App MVP
- 项目阶段：真实 AI 内测原型，可继续推进 TestFlight
- 角色定位：产品负责人 / 项目管理 / AI 协作式原型实现
- 案例版本：v1.0
- 日期：2026-07-04

## 1. 一句话介绍

热量咔是一款面向减脂用户的 AI 饮食记录 App。它用“拍照优先、文字补记兜底、实际摄入可调整”的方式，降低传统饮食记录中搜索食物、估算克数和逐项填写的负担。

推荐 slogan：

> 一拍就记，吃得明白。

## 2. 背景与问题

传统饮食记录 App 对用户的要求较高：需要搜索食物、选择素材库条目、填写克数、逐项添加。对中餐、复合菜和外食场景来说，这套流程很容易让用户因为“太麻烦”而放弃记录。

本项目选择的核心问题不是“做一个更全的食物数据库”，而是验证：

- 用户能否用拍照和自然语言更快完成一次饮食记录；
- AI 估算结果即使不完美，是否能通过清晰的不确定性表达和可编辑流程变得可用；
- 在真实 AI 接入后，用户是否能接受“快速记录 + 事后修正”的产品模式。

## 3. 我的职责

本项目采用多 Agent 协作方式推进，我承担项目管理部角色，同时主导产品判断与体验取舍：

- 明确 MVP 范围、排除项和质量门；
- 将用户反馈拆成产品规则、UI 修订、研发实现和 QA 复验；
- 持续把“真实用户会怎么理解”转化为可执行交互规则；
- 推动从 mock-only 原型升级到真实 AI 云端代理；
- 识别并处理隐私、安全、数据持久化、发布前质量等风险；
- 将每轮内测反馈收敛为更顺手的主链路体验。

## 4. 产品目标

MVP 的北极星目标是降低记录门槛，而不是追求营养估算的虚假精确。

核心目标：

- 从照片或文字提交到可保存记录的链路尽量短；
- 识别结果可编辑、可删除、可重新分析；
- 默认用自然单位表达份量，例如“1 个”“半碗”“1 根”；
- 明确区分真实 AI 结果与 fallback 示例结果；
- 用户能调整“实际吃了多少”，避免“照片里有多少 = 实际吃了多少”的误差。

## 5. 核心方案

### 5.1 主链路

主入口是底部相机按钮：

1. 用户点击相机按钮拍摄食物；
2. App 调用云端轻量代理；
3. DashScope/Qwen 识别图片食物；
4. App 展示确认页；
5. 用户可直接保存，或进入实际摄入调整；
6. 保存到本机饮食日记。

当照片识别失败或用户不方便拍照时，提供文字补记：

1. 用户输入自然语言，例如“早餐吃了一个鸡蛋和一碗米饭”；
2. DeepSeek 解析食物、份量和营养估算；
3. App 展示同一套确认页；
4. 用户保存或修正。

### 5.2 实际摄入调整

项目中一个关键产品问题是：照片里有两个鸡蛋和一碗米饭，但用户实际只吃了一个鸡蛋和一碗米饭，不能用整餐比例一刀切。

最终规则：

- 默认按识别份量全部计入，保持快速记录；
- 支持单项调整实际摄入；
- 支持整餐一起调整，但明确这是批量操作；
- 批量调整后仍允许单项覆盖；
- 文字修正可以表达“鸡蛋吃了一半”“把馒头改成玉米”等自然语言。

这个设计保留了快速记录，又避免用户感到“AI 记录不准确但我没法修”。

### 5.3 体重趋势

趋势页支持：

- 当前体重与目标体重；
- 最近 30 天体重趋势；
- 手动录入或更新今日体重；
- 体重历史本机保存；
- 日期选择和历史记录查看。

这部分的价值不是做复杂健康分析，而是让用户看到饮食记录之外的结果反馈。

### 5.4 数据与隐私

当前 MVP 的数据策略：

- 饮食记录、体重、目标等保存到本机 JSON 快照；
- App 不保存 Provider API Key；
- 原始食物照片不在 App 内长期保存；
- 用户可以删除单条记录，也可以删除全部本机数据；
- 营养结果明确标注为估算参考，不作为医疗建议。

## 6. AI 与技术架构

当前真实 AI 链路：

```text
iOS App -> 阿里云函数计算 Web 函数 -> DashScope / DeepSeek
```

职责拆分：

- iOS App：拍照、文字输入、确认页、实际摄入调整、本机持久化；
- HeatCalAIProxy：隐藏 Provider Key、归一化错误、校验结构化响应；
- DashScope/Qwen：图片食物识别；
- DeepSeek：文字补记和自然语言纠错；
- fallback：仅用于开发或故障兜底，并在 UI 中明确标记。

从本地代理升级到阿里云函数计算后，App 不再依赖 Mac 本机代理，真实内测体验更接近可分发产品。

## 7. 关键迭代

### 7.1 从 mock-only 到真实 AI

早期先交付 mock-only 内测原型，用于验证主流程、信息架构和实际摄入调整模型。随后接入 DashScope 和 DeepSeek，通过轻量代理保证 API Key 不进入 iOS App。

### 7.2 从“能用”到“用户知道发生了什么”

真实 AI 接入后，用户反馈“点了没反馈，以为没点到”。因此补充等待态：

- 按钮变为“正在分析...”；
- 输入框暂时不可编辑；
- 禁止重复提交；
- 超过一段时间后提示模型响应可能较慢。

这类反馈不改变能力，却显著降低用户的不确定感。

### 7.3 从设计稿到真机体验

真机复看中持续修正了：

- 底部 Tab 与相机主按钮的层级；
- 长按更多记录方式的提示；
- 日期滚轮的层级和可读性；
- 体重记录的输入效率；
- 实际摄入调整页的按钮一致性；
- AI 等待态和错误态文案。

这些细节体现了产品从“原型好看”走向“真机可用”的过程。

## 8. 验证证据

已完成的验证包括：

- 后端代理单元测试：8 项通过；
- 真实 DeepSeek 文字分析链路：通过；
- 真实 DeepSeek 纠错链路：通过；
- 真实 DashScope 图片分析链路：通过；
- iOS XCTest：多轮运行，最高记录 31 项通过；
- 本机持久化与删除闭环 QA：PASSED；
- 真实 AI 体验问题聚焦复验：PASSED；
- 敏感信息扫描：未发现 Provider Key 进入 iOS App 或构建产物。

这些不是商业数据，但能证明该项目已经从“概念”推进到“可运行、可测试、可迭代”的真实原型。

## 9. 当前限制

这个项目还没有正式上架，也没有规模化用户数据。因此作品集中应避免声称增长、留存或商业转化结果。

当前仍应诚实标注：

- 未进入 App Store 正式发布；
- 暂无真实规模化留存数据；
- AI 营养估算准确率尚未通过大样本验证；
- 图片分析速度仍受 Provider 和网络影响；
- 深色模式、账号体系、云同步和正式隐私合规仍待后续完善。

## 10. 作品集表达重点

建议把这个项目放在作品集中时，重点表达三件事：

1. **产品思维**：从用户记录摩擦出发，围绕快速记录、可控修正和不确定性表达设计 MVP。
2. **AI 产品落地能力**：不是停留在 prompt demo，而是做了真实 Provider、轻量代理、错误归一化和 fallback 边界。
3. **Vibe Coding 协作能力**：使用多 Agent 分工，将产品、UI、研发、QA 组织成可迭代流水线，并通过真机反馈持续收敛体验。

## 11. 推荐作品集结构

如果做成 Notion / 飞书 / 个人网站页面，可以按以下顺序：

1. 项目封面：一句话介绍 + 3 张核心截图；
2. 用户问题：为什么传统饮食记录难坚持；
3. 产品方案：拍照记录、文字补记、实际摄入调整；
4. 关键决策：为什么不追求素材库，为什么强调可修正；
5. AI 架构：iOS App、云端代理、DashScope、DeepSeek；
6. 迭代过程：从 mock-only 到真实 AI，再到真机体验修正；
7. 验证证据：测试、QA、真实链路；
8. 反思与下一步：如果继续推进，会补哪些正式发布能力。

## 12. 可直接使用的项目摘要

热量咔是我主导设计并通过 AI 协作开发的 iPhone 饮食记录 MVP，面向希望降低饮食记录负担的减脂用户。项目以“拍照优先、文字补记兜底、实际摄入可调整”为核心路径，接入 DashScope/Qwen 进行图片识别，接入 DeepSeek 进行文字补记和自然语言纠错，并通过阿里云函数计算轻量代理保护 Provider Key。项目完成了真实 AI 链路、本机持久化、删除闭环、错误兜底和多轮真机体验迭代，具备进入 TestFlight 小范围内测的基础。
