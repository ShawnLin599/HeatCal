# AI 饮食记录 iPhone App MVP 产品设计

- 文档类型：产品需求文档（PRD）
- 产品名称：热量咔
- 文档版本：v1.0
- 日期：2026-06-13
- 状态：已批准
- 面向平台：iPhone
- 首批用户：希望降低饮食记录负担的减脂人群

## 1. 产品概述

产品通过食物照片以及可选的文字或语音补充，让 AI 识别食物、估算实际摄入份量，并提供热量、蛋白质、碳水化合物和脂肪数据。

产品的核心价值不是提供一个更大的食物素材库，而是缩短饮食记录链路：

> 无需搜索食物，拍照后约 15 秒完成一次可用的饮食记录。

AI 估算无法替代称重或专业营养评估。产品需要诚实表达不确定性，同时保证大多数日常记录足够快捷。

## 2. 用户痛点

传统饮食记录 App 通常要求用户搜索食物、选择素材库条目、填写克数并逐项添加。常见问题包括：

- 记录步骤多，难以长期坚持；
- 素材库未收录用户实际吃到的菜品；
- 中餐和复合菜难以拆解；
- 用户通常不知道食物的准确克数；
- 用户为了追求精确而放弃记录。

## 3. MVP 目标

MVP 优先验证两件事：

1. 用户是否愿意持续使用产品记录饮食；
2. 拍照记录是否明显快于传统搜索式记录。

### 3.1 核心指标

- 北极星指标：每位用户每周成功记录饮食的天数；
- 效率指标：从提交照片或文字到保存记录的中位时间不超过 15 秒；
- 留存指标：首次使用后第 7 天是否仍在记录；
- 使用指标：每日记录次数；
- 摩擦指标：分析后放弃率、修改频率、重新分析频率和主动追问频率；
- 质量指标：AI 首次结果直接采用率；
- 系统指标：AI 平均响应时间、失败率和单次调用成本；
- 体验指标：整餐贴纸是否提升日记回看和继续记录的意愿。

首轮稳定内测除产品创建者本人外，邀请约 5 至 10 位减脂用户连续使用一周，以减少熟悉产品带来的判断偏差。

## 4. 产品原则

1. **快速优先**：默认让用户以最少操作完成记录。
2. **用户可控**：所有 AI 结果均可修改、删除或重新分析。
3. **不制造虚假精确**：展示可信度、估算范围和主要误差来源。
4. **自然表达优先**：使用“个、片、杯、瓶、半碗”等自然单位，不强迫用户填写克数。
5. **AI 不确定性不转嫁给用户**：复杂菜品的内部拆解不要求用户逐项确认。
6. **先验证核心闭环**：不在 MVP 中加入会重新形成素材库负担的功能。

## 5. 核心用户流程

### 5.1 首次使用

1. 用户填写性别、年龄、身高、当前体重、目标体重和活动水平；
2. 系统生成每日建议热量和三大营养素目标；
3. 用户可手动修改目标；
4. 系统明确提示：营养结果属于健康参考和估算，不是医疗建议；
5. 用户进入“今日”页开始记录。

系统不得生成明显不安全的极低热量目标。目标计算规则和安全下限作为独立模块实现，便于后续调整。

### 5.2 拍照记录

1. 用户拍照或从相册选择照片；
2. 用户可选填文字，或通过系统语音转文字补充信息；
3. AI 分析食物、份量、做法、预计实际摄入比例和营养数据；
4. 系统展示分析确认页；
5. 用户直接保存，或进行纠错和份量调整；
6. 记录保存到对应日期和餐段；
7. 系统异步生成整餐贴纸，不阻塞保存。

### 5.3 纯文字或语音补记

用户不方便拍照、已经吃完或忘记记录时，可以直接输入：

> 昨晚加餐吃了一个苹果。

AI 提取食物、份量、日期、时间和餐段，并生成可确认的记录。没有照片的记录使用默认食物图标，不生成贴纸。

### 5.4 包装食品

1. 用户正常拍摄包装食品；
2. AI 先给出估算结果；
3. 产品可提示“补拍营养成分表可提高准确度”；
4. 用户可以跳过，也可以补拍；
5. 系统读取每 100 克、每份、净含量及三大营养素并重新计算。

MVP 不支持条形码。条形码只提供商品编号，仍依赖商品数据库，与产品减少素材库依赖的方向不一致。

### 5.5 实际摄入量

照片中的食物不一定等于用户实际吃掉的食物。保存前支持选择：

- 全部；
- 约四分之一；
- 约一半；
- 约四分之三；
- 自定义数量或比例。

共享菜品允许用户补充“我大约吃了四分之一”。保存后如果出现剩余，用户可以修改实际摄入量。MVP 不做餐前、餐后照片自动差值计算。

## 6. 信息架构

### 6.1 今日

- 展示当日已摄入和剩余热量；
- 展示蛋白质、碳水化合物和脂肪进度；
- 按早餐、午餐、晚餐和加餐分组；
- 每个餐段可包含不限数量的独立记录；
- 餐段默认折叠展示汇总，展开后展示每次记录；
- 支持进入过去日期补记或修改历史记录；
- 不允许创建未来饮食记录。

早餐、午餐、晚餐和加餐是记录分组，不是单条记录。用户早上先拍两个鸡蛋，十分钟后再拍一杯拿铁，两次记录均可归入早餐并分别编辑。

### 6.2 记录入口

主入口为拍照。首页同时提供权重较低的文字或语音补记入口。

支持：

- 相机拍摄；
- 相册选择；
- 文字补充；
- 系统语音转文字；
- 包装食品补拍营养成分表。

### 6.3 分析确认

展示：

- 整餐热量和三大营养素；
- 每项食物的名称、自然份量和营养数据；
- 可信度；
- 估算范围；
- 主要误差来源；
- 所属日期、时间和餐段；
- 实际摄入比例；
- “提高准确度”入口。

支持：

- 修改名称、数量和单位；
- 增加或删除食物；
- 修改日期、时间和餐段；
- 文字或语音纠错；
- 重新拍照；
- 重新分析；
- 保存记录。

### 6.4 趋势与设置

- 每日体重录入；
- 简单体重趋势图；
- 身体数据和减脂目标；
- 每日热量和三大营养素目标；
- 快速模式和精确模式；
- 本地数据删除；
- 隐藏开发者设置。

## 7. AI 分析与营养计算

### 7.1 推荐方案：分层估算

AI 负责理解照片和自然语言，营养计算模块负责尽可能稳定地计算结果。

#### 简单食物

苹果、鸡蛋、米饭和饮料等食物按识别出的种类与份量，结合标准营养参考数据计算。

#### 常见复合菜

宫保鸡丁、盖饭和炒菜等复合菜按整道菜和整份份量估算。系统可以在内部使用典型做法、食材构成和用油假设，但不要求用户提供鸡肉、花生或油的具体克数，也不向用户暴露复杂内部拆解。

#### 无可靠参考的食物

营养参考无法覆盖时，允许 AI 直接估算作为兜底，并降低可信度、扩大估算范围、说明不确定因素。

### 7.2 自然份量模型

用户看到的份量由以下部分组成：

> 数量 × 自然单位 × 可选单位大小

示例：

- 苹果：1 个，中等大小；
- 鸡蛋：2 个；
- 米饭：半碗；
- 可乐：1 瓶，500 毫升；
- 奶茶：1 杯，中杯，喝了约一半；
- 红烧肉：6 块。

系统内部将自然单位换算为克或毫升，用于营养计算。用户可以修改数量、单位或单位大小。

### 7.3 快速模式与精确模式

#### 快速模式

- 默认模式；
- AI 直接给出结果；
- 仅在信息缺失会严重影响结果时追问；
- 用户可跳过问题，直接采用当前估算。

#### 精确模式

- AI 主动询问对结果影响较大的信息；
- 例如饮料容量、是否含糖、是否重油、实际吃掉比例；
- 用户始终可以跳过；
- 设置决定默认模式，单次记录不要求先选择模式。

### 7.4 追问原则

AI 只询问用户容易回答、且会明显改变结果的问题，例如：

- “这杯饮料是中杯还是大杯？”
- “这道菜是正常用油还是少油？”
- “这份共享菜你大约吃了多少？”

AI 不询问用户通常无法回答的问题，例如：

- “宫保鸡丁中有多少克鸡肉？”
- “这道菜用了多少克食用油？”

### 7.5 可信度与估算范围

每次分析返回：

- 一个便于记录的主估算值，例如“约 620 千卡”；
- 可信度：较高、一般或较低；
- 必要时展示可能范围，例如“约 520 至 760 千卡”；
- 主要误差来源，例如“炒菜用油量未知”。

用户修改份量或实际摄入比例后，系统本地按比例重新计算，不再次调用 AI。只有自然语言纠错或重新分析时才调用 AI。

### 7.6 结构化输出与校验

AI 必须返回固定结构的数据，至少包括：

- 食物项；
- 自然份量；
- 内部换算重量或容量；
- 热量和三大营养素；
- 可信度和估算范围；
- 主要误差来源；
- 建议追问；
- 识别出的日期、时间和餐段。

客户端或后端必须验证数据结构和数值合理性。结构错误、缺失字段或明显异常值不得直接保存为正式记录。

## 8. 纠错、编辑与复用

### 8.1 自然语言纠错

用户可以输入或说：

- “这不是猪肉，是牛肉。”
- “漏了一杯无糖豆浆。”
- “米饭只有半碗。”
- “这道菜没有放油。”
- “删除右边那份甜点。”

系统重新分析并更新结果。

### 8.2 基础编辑

每项食物支持修改名称、数量、单位和营养数据，也支持添加和删除。每条已保存记录支持修改、删除、更换餐段和重新分析。

### 8.3 轻量复用

MVP 仅支持：

- 复制上一餐；
- 复制昨日同餐；
- 复制后逐项编辑。

MVP 不支持常用餐食模板，也不自动判断两张照片是否属于相同餐食。内测时观察用户是否频繁记录相似餐食，再决定是否加入模板或历史推荐。

## 9. 整餐贴纸

每次带照片的记录生成一张整餐贴纸，用作饮食日记缩略图。

要求：

- 贴纸生成异步执行，不阻塞分析和保存；
- 以整餐或餐盘为对象，不尝试逐项拆分复杂食物；
- 添加较粗白边以形成统一视觉风格，并弱化抠图误差；
- 抠图失败时自动降级为圆角原图缩略图；
- 无照片记录使用默认食物图标。

贴纸的 MVP 目标是增强记录反馈感和日记回看意愿，而不是实现精准图像分割。

## 10. 失败处理

### 10.1 照片模糊或无法识别

- 提示重拍；
- 允许补充文字后继续分析；
- 允许转为纯文字记录。

### 10.2 AI 服务或网络异常

- 将照片和描述保存为“待分析记录”；
- 网络恢复后允许用户重试；
- 不因单次失败丢失用户输入；
- 待分析记录不计入正式营养汇总，完成分析并确认后才计入。

### 10.3 部分识别错误

- 优先提供自然语言纠错；
- 同时提供基础按钮编辑；
- 最后提供重新拍照或重新分析。

### 10.4 贴纸失败

贴纸生成失败不影响饮食记录。系统直接使用圆角原图。

## 11. 数据模型

### 11.1 主要实体

#### UserProfile

- 身体数据；
- 减脂目标；
- 活动水平；
- 每日热量和三大营养素目标；
- 默认记录模式。

#### MealEntry

一次独立记录，可由照片、文字或语音创建。

- 日期与时间；
- 餐段；
- 原始照片引用；
- 整餐贴纸或降级缩略图；
- 原始文字补充；
- 实际摄入比例；
- AI 分析状态；
- 可信度与误差说明；
- 多个 FoodItem；
- 创建与修改时间。

#### FoodItem

- 显示名称；
- 数量；
- 自然单位；
- 单位大小；
- 内部换算重量或容量；
- 热量；
- 蛋白质；
- 碳水化合物；
- 脂肪；
- 数据来源与可信度。

#### WeightEntry

- 日期；
- 体重；
- 创建与修改时间。

### 11.2 汇总规则

- 餐段汇总其下所有 MealEntry；
- 当日汇总所有正式 MealEntry；
- 待分析记录不参与汇总；
- 编辑或删除记录后立即更新汇总；
- 历史记录修改后重新计算对应日期。

## 12. 系统组件与边界

### 12.1 iPhone 客户端

负责：

- 相机、相册、文字和系统语音转文字输入；
- 今日页、记录确认页、趋势页和设置页；
- 本地数据持久化；
- 本地营养比例重算；
- 本地图片与贴纸管理；
- API 密钥的安全存储；
- 离线待分析队列；
- 匿名性能指标采集。

### 12.2 AI Provider 接口

产品内部使用统一 AI Provider 接口，至少提供：

- 食物照片分析；
- 文字补记分析；
- 自然语言纠错；
- 营养成分表读取；
- 整餐贴纸生成或调用。

默认用户不接触模型配置。隐藏开发者设置允许内测者配置经过测试的厂商、模型名称、接口地址和自带 API 密钥，用于比较模型效果和控制内测成本。

自带 API 密钥仅保存在 iPhone 钥匙串中。产品必须明确提示请求会发送至对应模型厂商。MVP 普通用户界面不开放自带 API 密钥配置。

### 12.3 轻量后端

默认 AI Provider 通过轻量后端调用，避免在 App 中暴露产品方 API 密钥。后端负责：

- 请求鉴权与限流；
- AI 请求转发；
- 提示词和结构化输出版本管理；
- 响应校验与错误归一化；
- 记录不包含饮食内容的性能与成本指标；
- 完成分析后不长期保存用户照片。

### 12.4 营养计算模块

负责：

- 自然单位到克或毫升的换算；
- 标准营养数据计算；
- 复合菜典型整份估算；
- 用户调整后的即时比例重算；
- 数值合理性检查。

该模块与 AI Provider 解耦，便于后续替换模型或营养参考来源。

## 13. 数据与隐私

- 内测阶段无需注册；
- 目标、饮食、体重和本地图片保存在设备本机；
- 卸载 App 或更换手机会丢失数据，首次使用时明确提示；
- 食物照片可以发送至云端 AI 分析；
- 产品方后端完成分析后不长期保存照片；
- 用户可以删除单条记录、本地照片和全部数据；
- 相机、相册和麦克风权限仅在使用对应功能时申请；
- 匿名指标不得包含饮食照片、用户原文、身体数据或 API 密钥；
- 产品明确标注营养数据为估算值，不作为医疗建议。

MVP 不提供账号、云同步、跨设备恢复或数据导出。

## 14. 健康与安全边界

- 每日目标计算设置合理安全下限；
- 不鼓励极端节食或过度追求单日数字；
- 对特殊疾病、孕期、饮食障碍或医疗营养需求用户提示寻求专业建议；
- 可信度较低时不得以无提示的精确数字误导用户；
- 体重趋势只提供简单展示，不给出医疗判断。

## 15. MVP 范围

### 15.1 包含

- 无需注册和本机数据保存；
- 身体数据、减脂目标和每日营养目标；
- 拍照、相册、纯文字和语音补记；
- AI 食物识别、自然份量和营养估算；
- 快速模式、精确模式和可跳过追问；
- 可信度、估算范围和误差来源；
- 包装食品可选补拍营养成分表；
- 实际摄入比例调整；
- 历史日期补记；
- 识别结果纠错、保存后编辑和重新分析；
- 早餐、午餐、晚餐和加餐下的多条独立记录；
- 复制上一餐和昨日同餐；
- 异步生成整餐贴纸；
- 每日摄入进度、剩余额度和简单体重趋势；
- 隐藏开发者设置中的模型切换和自带 API 密钥；
- 离线待分析记录和失败重试。

### 15.2 明确不包含

- 条形码识别；
- 常用餐食模板；
- AI 自动识别历史相同餐食；
- 复杂菜品逐项食材确认；
- 将复杂菜品拆成多个独立贴纸；
- 餐前、餐后照片自动差值计算；
- 账号、云同步和跨设备恢复；
- 数据导出；
- Apple Health 接入；
- 提醒通知；
- 社区、食谱推荐和复杂健康分析；
- 商业化、订阅和普通用户自带 API 密钥界面。

## 16. 测试策略

### 16.1 产品场景测试

使用一组固定场景重复内测：

- 单一食物：苹果、鸡蛋、米饭；
- 饮料：瓶装饮料、咖啡、奶茶；
- 常见中餐复合菜；
- 多菜同盘；
- 多人共享菜；
- 包装食品和营养成分表；
- 模糊照片；
- 忘记拍照后的历史文字补记；
- 一餐分多次记录；
- 吃完后修改实际摄入量；
- AI 与网络失败；
- 贴纸生成失败。

### 16.2 功能测试

- 餐段和当日汇总正确；
- 修改数量、单位和摄入比例后本地重算正确；
- 历史日期识别和手动修改正确；
- 待分析记录不进入营养汇总；
- 删除和重新分析不会产生重复记录；
- 快速模式和精确模式行为符合定义；
- 自带 API 密钥安全存储且不写入日志；
- 删除全部数据后本地内容清除。

### 16.3 AI 质量评估

为固定测试照片保留人工参考结果，对不同模型和提示词版本比较：

- 食物识别覆盖率；
- 严重误识别率；
- 热量和三大营养素误差范围；
- 自然份量合理性；
- 追问是否必要；
- 结构化输出成功率；
- 平均响应时间与成本。

## 17. 后续迭代假设

以下能力只有在内测数据支持时才进入后续版本：

- 常用餐食模板或历史相似餐食推荐；
- 单项食物收藏；
- 更多 AI Provider 和普通用户自带 API 密钥；
- 账号、云同步和跨设备恢复；
- Apple Health 与体重设备接入；
- 提醒和连续记录激励；
- 更精细的复合菜估算；
- 个性化学习用户餐具、份量和修正习惯；
- 更复杂的体重与营养趋势分析；
- 商业化和订阅。

## 18. MVP 验收定义

MVP 可以进入首轮连续内测，需要同时满足：

1. 用户可以完成首次目标设置；
2. 用户可以通过照片或纯文字创建、纠错、保存和修改记录；
3. 同一餐段可以包含多条记录，并正确汇总；
4. AI 失败不会导致用户输入丢失；
5. 大多数标准测试场景可以在约 15 秒内完成记录；
6. 每条结果明确表达估算性质和不确定性；
7. 体重录入和趋势可正常使用；
8. 默认 AI Provider 不暴露产品方 API 密钥；
9. 隐藏开发者设置可以切换经过测试的模型；
10. 产品可以采集不包含敏感饮食内容的核心内测指标。
